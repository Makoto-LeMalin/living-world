# 工作规范（Process）

| 项 | 内容 |
|---|---|
| 版本 | v1.0（2026-11-16） |
| 状态 | 生效；任何阶段开工前必须遵守 |
| 上位 | [`AGENTS.md`](../AGENTS.md) |
| 目的 | 把“组织 / 设计 / 开发 / 测试 / 审计”拆成互斥角色，禁止自审，保证交接物可复核 |

---

## 1. 适用范围

适用于本仓库的一切阶段工作：M0–M6、R0 门禁修复、demo 迭代、文档重写、设计评审。

不适用于纯阅读、提问、单次事实查询；一旦开始改文件或下结论，即适用。

---

## 2. 角色定义

### 2.1 Coordinator（工作组织）

- 拆分阶段、写任务卡、维护角色矩阵；
- 分派执行/测试/审计代理；
- 检查交接物是否齐全，宣布阶段准入/不准入；
- **不做**设计、开发、测试、审计。

### 2.2 Document Manager（文档管理）

- 维护决策记录、任务索引、审计索引、链接与术语表；
- 登记其它会话产出的设计文档，**不改写设计内容**；
- 发现文档与代码漂移时，登记为待修项，不自行判断技术正确性。

Coordinator 与 Document Manager 可由同一会话承担；文档管理不属于“设计/开发/测试/审计”四类，故不冲突。具体分工由阶段任务卡记录，不写死某个会话。

### 2.3 Designer（设计）

- 产出需求/架构/机制/世界卡/提示词设计；
- 给出验收标准、边界、失败分支；
- **不做**实现、测试、审计。

设计产物必须带：版本、日期、输入决策、未决问题、可验收标准。

### 2.4 Implementer（开发）

- 只按已批准设计/任务卡写代码；
- 记录改动文件、运行命令、已知限制；
- **不做**设计决策、不签测试、不自审；
- 若实现必须改变设计，停止并转设计会话。

### 2.5 Verifier（测试）

- 在独立环境/独立进程中重跑验收命令；
- **评估测试本身**：测试是否真的验证了目标行为、是否自证/同义反复、断言是否足够强；不能只重跑一次就下结论；
- **评估覆盖**：列出修订模块的分支/边界/负向路径，实际打探针，指出未覆盖分支；
- **评估稳定性与真实性**：重复运行、顺序依赖、时间/网络依赖、输出解析是否可靠；
- 可写独立测试/临时探针（不修改产品代码），报告实测与阅读判断的区别；
- 写验证报告：环境、命令、输出、测试有效性/覆盖矩阵、未验证项；
- **不修改产品代码**；
- 不得与 Implementer 为同一 agent。

### 2.6 Auditor（审计）

- 只读代码、提交、报告、运行记录；
- 独立判断技术结论与流程结论；
- 写审计报告，给 PASS / CONDITIONAL PASS / FAIL；
- **不参与**设计、实现、测试；
- 不得审计自己参与过的阶段。

---

## 3. 角色互斥规则

1. 同一阶段内，一个 agent 只能出现在角色矩阵的一列。
2. 出现两列及以上 → 该阶段流程无效，停止，重新分派。
3. Auditor 必须独立于该阶段的设计、实现、测试。
4. Coordinator 可以分配任务，但不能替任何角色完成其产出。
5. “顺手改一下”视为跨角色；不允许。

---

## 4. 阶段协议

### 4.1 阶段开工前

必须有 `docs/tasks/<stage>.md`，至少包含：

- 目标与非目标；
- 输入（设计文档/审计报告/决策记录）；
- 角色矩阵（Coordinator / Designer / Implementer / Verifier / Auditor）；
- 允许写入的路径；
- 验收标准与证据要求；
- 停止条件。

没有角色矩阵 → 不开工。角色矩阵中出现重复 agent → 不开工。

### 4.2 设计交接

设计来自指定设计会话。登记时必须记录：

- 设计文档路径与版本；
- 它依据的决策编号（`docs/DECISIONS.md`）；
- 未决问题；
- 它明确不覆盖的范围。

Coordinator 只登记，不替设计会话补写内容。

### 4.3 实现交接

Implementer 必须提交：

- 改动文件列表；
- 运行过的命令与结果；
- 已知限制/未覆盖项；
- 是否触碰任务卡 write scope 之外的路径（默认禁止）。

### 4.4 验证交接

Verifier 必须在**独立环境**重跑，不接受“实现者说跑过了”。

验证报告至少包含：

- 环境（Node 版本、commit、工作区状态）；
- 命令与退出码；
- 关键输出；
- 未验证项；
- 是否发现实现者未声明的改动。

### 4.5 审计交接

Auditor 只读，输出：

- 技术结论；
- 流程结论；
- 阻断/重要/次要发现；
- 准入条件；
- 未验证项。

只有 Auditor 可以签“阶段通过”。

### 4.6 准入

Coordinator 根据 Auditor 结论登记准入。技术通过但流程失败 → 仍不准入。

---

## 5. 证据规则

1. **命令可重跑**：所有数字必须来自可重跑命令。
2. **基线不可自证**：`verify` 不能先写基线再宣称基线未变；必须有独立期望值或 diff 失败门。
3. **测试数不硬编码**：从实际输出解析。
4. **门有期望集合**：`expectedGateIds` 与报告做集合相等，不能 `${n}/${n}`。
5. **字节级声明需要字节样本**：只有 32 位哈希时，只能写“内容哈希一致”。
6. **未验证就写未验证**：不得用“应该/理论上/通常”替代证据。
7. **不打印密钥**：`.env` 只确认是否被跟踪，不读内容。

---

## 6. 变更控制

- 需求/设计变更 → 设计会话出新版本，登记到 `docs/DECISIONS.md`；
- 实现变更 → 只走 Implementer；
- 测试标准变更 → 由 Designer 更新验收标准，Verifier 执行；
- 审计标准变更 → 由 Auditor 提出，Coordinator 登记；
- Coordinator 不改写设计，只登记与索引。
