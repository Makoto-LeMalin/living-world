| 项 | 内容 |

---

## 1. 背景

当前项目没有“世界卡”这个一等模块。提示词、语气、限制、世界前提、角色钩子散落在 PRD、世界 canon、角色设定和 system prompt 中，导致：

- 世界与角色的提示词难写、难复用、难迁移；
- 限制类提示词没有独立归属；
- Channel、世界、角色之间的边界靠约定，无法验收；
- 用户无法选择/替换“这个世界怎么被讲述”。

用户已明确：

- 世界卡（World Card）是**独立于世界与角色**的模块，但与两者联动；
- 限制提示词属于世界卡/提示词模块的一部分；
- 框架不提供审核服务；内容边界可由世界文本/世界卡承载；
- 目标是**更 easy 的世界/角色提示词编写方案**；
- 不替用户决定 Channel / 内容边界的默认值。

本任务只做设计，不写实现、不写代码、不写测试、不做审计。

---

## 2. 设计目标

产出一份可执行的设计，回答两件事：

1. **世界卡的结构**：它由哪些部分组成，每部分负责什么，如何组合、版本化、校验、编写。
2. **世界卡敲定什么**：哪些东西由世界卡决定，哪些留给世界实例，哪些留给角色，哪些留给 Channel/用户选择。

必须给出与以下对象的显式契约：

- **World**：世界卡向世界提供什么；世界向世界卡提供什么；冲突时谁优先。
- **Character**：世界卡向角色提供什么（语气、角色钩子、限制、可用模块）；角色保留什么；覆盖规则。
- **Prompt Composer / LLM 层**：模块如何拼装、排序、裁剪、冲突检测、token 预算。
- **Channel**：世界卡可否建议/限制 Channel 预设；用户选择如何覆盖；不得把 A/B/C 写死。
- **Authoring / Validation**：作者如何写、如何预览、如何发现错误；如何保持“easy”。

---

## 3. 非目标

- 不实现任何代码、类型、schema 文件、CLI、UI。
- 不提供内容审核服务；不设计静默过滤。
- 不重写 Channel 设计；不决定 A/B/C 的默认值。
- 不重写世界 canon、角色 persona、事件系统。
- 不决定具体世界内容（地名、势力、剧情）。
- 不做迁移脚本或运行时改造。
- 不把旧 PRD 的 D6 / R-CH4 当作需求权威。

---

## 4. 必须回答的设计问题

### 4.1 定义与边界

- 世界卡是什么？是按世界、按场景、按会话，还是可复用的内容包？
- 它与 `canon`、世界种子、角色卡、ChannelProfile、system prompt 的关系是什么？
- 一张世界卡的最小单位是什么？是否允许多张卡组合（base + variant）？
- 哪些内容**必须**在世界卡，哪些**必须**在世界，哪些**必须**在角色？给判定规则，不只给例子。

### 4.2 预期结构

设计文档必须给出结构提案，至少覆盖：

- 身份与元数据：id、名称、版本、作者、许可证、兼容性、语言；
- 世界前提：类型、时代、基调、尺度、禁忌、世界运行规则；
- 内容 envelope：分级/主题/禁区/用户同意（声明，不是服务）；
- 提示词模块：系统提示、风格指南、限制模块、少量示例、校验规则等；给出模块分类与组合规则；
- 角色钩子：可扮演角色类型、角色可用/不可用的设定、语气与称呼规则；
- Channel 钩子：可建议/限制的通信形式；不得覆盖用户选择；
- 世界钩子：地点/势力/事件类型/规则扩展点；
- 作者说明与示例：如何写、如何改、如何复用；
- 校验与版本：schema/语义校验、冲突检测、迁移策略。

### 4.3 契约与优先级

必须明确：

- 世界卡 vs 世界 canon：谁能覆盖谁？世界卡能否改 canon？canon 能否违反世界卡？
- 世界卡 vs 角色：角色能否覆盖世界卡的语气/限制？哪些字段不可覆盖？
- 世界卡 vs Channel：用户选择 Channel 时，世界卡的限制是硬约束、建议，还是仅提示？
- 世界卡 vs Prompt Composer：模块顺序、冲突检测、token 预算、缺失模块的默认行为；
- 世界卡 vs 内容边界：声明性 envelope 与宿主策略如何分工；框架不做审核服务。

给出一张**“谁敲定什么”矩阵**：行是信息类型，列是 World Card / World / Character / Channel / User，单元格写“决定/默认/可覆盖/不可覆盖”。

### 4.4 组合、版本与迁移

- 是否支持基础卡 + 变体卡 + 角色卡 + 场景卡的组合？
- 冲突如何检测、如何呈现、如何裁决？
- 世界实例如何引用世界卡版本？卡升级后旧世界怎么办？
- 是否允许用户覆写？覆写如何记录、如何回放？
- 世界卡是否进入世界配置/hash，保证同存档可复现？

### 4.5 编写体验

- 作者用什么格式写（Markdown/YAML/JSON/其它）？为什么？
- 如何做到“easy”：模板、片段、继承、预览、错误提示、示例库、AI 辅助？
- 非工程师能否只写世界文本就得到可用卡？
- 如何避免提示词注入、复制粘贴漂移、模块互相矛盾？
- 如何验证“这张卡真的改变了世界/角色的行为”，而不是只存在文件里？

### 4.6 失败模式

至少分析：

- 卡缺失/字段缺失/未知版本；
- 卡与 canon 冲突；
- 卡与角色冲突；
- 卡与 Channel 冲突；
- 模块顺序错误/token 超限；
- 限制模块被绕过或产生自我审查；
- 多卡组合冲突；
- 卡升级导致旧存档不可复现；
- 作者写了“好设定”但模型不遵守。

---

## 6. 验收标准

设计审计通过的最低条件：

- [ ] 世界卡被定义为独立模块，不硬编码进世界或角色；
- [ ] 结构覆盖元数据、世界前提、内容 envelope、提示词模块、角色/Channel/世界钩子、校验/版本；
- [ ] 与世界、角色、Channel、Prompt Composer 的契约明确，冲突有裁决规则；
- [ ] “谁敲定什么”矩阵完整，能回答“这张卡敲定什么”；
- [ ] 支持用户选择/覆写，且不替用户决定 Channel/内容默认值；
- [ ] 限制提示词明确属于世界卡/提示词模块，不是独立审核服务；
- [ ] 编写体验方案可执行，不是“写得更清楚”这种口号；
- [ ] 组合/版本/迁移/失败模式有可操作方案；
- [ ] 至少 4 个示例，展示“敲定/不敲定”；
- [ ] 明确列出未决问题，不把猜测写成结论；
- [ ] 不含实现代码；不修改现有设计/验收标准。

## 9. 停止条件

出现任一项，停止并上报 Coordinator：

- 设计需要改代码/写实现；
- 设计试图决定 Channel A/B/C 的默认值或内容分级默认值；
- 设计把内容审核服务引入框架；
- 设计把世界卡硬编码进世界/角色；
- 设计需要改旧 PRD 才能成立（应先登记新决策）；
- 设计无法给出“谁敲定什么”的明确规则，只能给例子。
