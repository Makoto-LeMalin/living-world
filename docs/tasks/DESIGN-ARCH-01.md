---

## 1. 任务性质

这是一次**重新裁决**，不是对旧架构文档的修订。

旧的设计文档、计划文档、任务卡和模块依赖矩阵已从工作区清理。它们不再作为输入，也不要在 git 历史里恢复后照抄。请从以下三样东西出发：

1. 产品需求（PRD）；
2. 用户决定（DECISIONS）；
3. 当前代码与测试所证明/未证明的事实。

---

## 2. 关键约束

**本任务卡刻意不列模块清单，也不给分层名称。**

架构设计的第一步就是判断：

- 系统边界在哪；
- 哪些概念属于同一职责；
- 哪些必须分开；
- 哪些依赖方向必须禁止；
- 哪些是运行期、哪些是编辑期/生成期。

如果你一上来就套用某个现成的模块划分（例如 kernel/space/world/characters/rules/app/host），那这次设计就失败了。你需要自己提出划分，并给出理由与被否决的替代方案。

---

## 3. 必须回答的问题

### 3.1 需求与质量属性

- PRD 中哪些是硬约束，哪些是可配置项，哪些尚未决？
- 哪些质量属性是架构级驱动因素：可回放、可测试、可替换宿主、成本上限、延迟、故障隔离、可演进？
- 这些属性冲突时怎么取舍？拒绝哪些方案，为什么？

### 3.2 领域概念与不变量

- 世界真相、角色认知、用户消息、事件、事实、记忆、人格等概念之间，哪些不变量必须成立？
- 哪些状态是权威的，哪些是投影/缓存/索引？
- 哪些行为必须可回放，哪些允许不确定？

### 3.3 边界与分解

- 系统与宿主、应用、领域、基础设施的边界如何划？
- 分解成哪些部分？每部分的职责、输入、输出、不做什么？
- 为什么这样分，而不是另一种分法？至少给两个被否决的替代方案。
- 依赖方向、循环依赖、跨边界数据传递如何约束？

### 3.4 数据流、写路径与回放

- 外部输入（用户、宿主、LLM 提案）如何进入系统？
- 什么是唯一写路径？谁有权裁决结果？
- 事件/快照/回放/迁移的关系；同 seed 可复现的边界。
- 事件 schema、版本、兼容策略。

### 3.5 运行时

- tick/clock：开发、应用、暂停、加速、离线推进；
- 调度者的单写者/幂等；
- 同步规则与异步 LLM 的边界、超时、回退、预算、降级；
- 失败隔离：LLM/宿主/存储不可用时，什么继续、什么降级。

### 3.6 契约

- 各组成部分之间的数据/控制契约；
- 谁拥有什么状态，谁只能读，谁只能提案；
- 用户消息/角色认知/世界事实之间的边界；
- 生成期（内容/配置/世界卡）与运行期的边界；
- 配置、版本、存档如何随世界走。

### 3.7 存储、宿主与演进

- 开发期与生产期存储的边界；迁移策略；
- 宿主适配器能做什么、不能做什么；移除宿主后什么仍可运行；
- 多世界/单世界、单用户/多用户的边界；
- schema/协议/配置的演进与回滚。

### 3.8 当前代码的差距

- 两个 demo 与 `src/` 当前证明了什么、没证明什么；
- 哪些代码保留、迁移、废弃；
- 从当前状态到目标架构的阶段、门槛、回滚、失败分支。

### 3.9 后续设计的依赖

- 架构需要哪些后续设计（世界、角色、Channel、世界卡等）来补齐细节？
- 哪些决定必须先于它们，哪些可以后置？
- 给出依赖矩阵，但不要替用户决定实现顺序。

## 4. 交付物

`docs/design/ARCHITECTURE.md`，至少包含：

- 需求/质量属性驱动因素；
- 领域概念与不变量；
- 系统边界与分解（含替代方案与否决理由）；
- 数据流/写路径/回放；
- 运行时与失败模式；
- 契约与依赖规则；
- 存储/宿主/配置/演进；
- 当前代码差距与迁移阶段；
- 后续设计依赖矩阵；
- 架构决策记录（ADR 风格）；
- 未决问题。

可以附伪 TypeScript 接口；不要写实现代码。

- [ ] 覆盖 PRD 的硬约束与 D-001–D-008；
- [ ] 世界真相/角色认知/用户消息的边界明确；
- [ ] 唯一写路径、回放、事件版本策略明确；
- [ ] 运行时、异步 LLM、预算、失败回退明确；
- [ ] 契约与依赖规则明确，能指导实现；
- [ ] 存储/宿主/配置/演进有可执行方案；
- [ ] 当前代码到目标架构的迁移阶段与门槛可执行；
- [ ] 后续设计依赖矩阵可支撑顺序决策；
- [ ] 未决问题明确；不含实现代码；
- [ ] 独立 Auditor 通过。

## 8. 停止条件

- 设计从旧模块划分/旧架构文档出发，而不是从需求与代码出发；
- 设计只是给旧架构换名字；
- 设计需要写代码/测试才能成立；
- 设计替用户决定产品内容、Channel 默认值或实现顺序；
- 设计无法给出替代方案与否决理由；
- 设计把未验证的 demo 机制当成产品质量证明。
