### 1.4 环境噪声（不影响结论，但必须写明）

## 4. 测试有效性评估（新增）

### 4.1 结论：不是“重跑即通过”，也不完全是自证闭环，但有 5 个已实测的边界

**已消除的自证闭环（实测 + 阅读）**

| 原缺陷 | 现状 | 证据 |
|---|---|---|
| `verify` 最后一步重写 tracked 基线，之后无 diff 断言 | `verify` 最后一步是 `check:baseline`（对照）；CI 额外有 2 条 `git diff --exit-code` | C8/C9、P17 |
| 测试数硬编码 `{100,67,27,194}` | 删除；`runSuites` 重跑并解析输出 | §3.2、N3b |
| `门：${gates}/${gates}` 恒等式 | 改为 `passed/expected` + `expectedGateIds` 集合相等 | §3.3 |
| 无 CI | 有，且顺序合理 | §3.4 |

**仍然存在的 5 个边界（都是实测，不是推测）**

1. **`test.skip` 不被判红（N3a）**：把 `test/clock.test.ts` 首个 `test(` 改成 `test.skip(` 后，`pnpm test:all` 输出 `ℹ tests 27 / ℹ pass 26 / fail 0`，`total=194`，exit 0；`check:baseline` **仍 exit 0**。原因：门只比较 `tests` 计数与 `fail === 0`，没有比较 `pass === tests`，也没有断言 `skipped === 0`。`baseline.md` 的“27 通过”实际是 `tests` 计数，措辞略宽。
2. **`check:baseline` 单命令不自足（P12）**：报告 JSON 是它的输入，它从不重新生成、也不检查新鲜度。探针：把 `cli.ts` 的 `runValidation({ seeds: 20, days: 3 })` 改成 `days: 2`（**不动**报告）→ `check:baseline` **exit 0**；再运行 `report` 重新生成后 → **exit 1**（`b2.events: 期望 668 实际 437`、来源分布、三个 hash 全变）。也就是说：**只有 `pnpm verify`（含 `report` 步骤）才是端到端门**；单独跑 `pnpm check:baseline` 或 `pnpm baseline` 时，若报告是旧的，会假绿。
3. **本地 `verify` 不检查工作区干净（P17）**：改 `scripts/baseline.mjs` 中 `baseline.md` 的固定文案后跑 `pnpm verify` → **exit 0**，但 `git status` 出现 ` M reports/baseline.md`；同一状态下 `git diff --exit-code -- reports/baseline.md` → **exit 1**。即“本地绿 ≠ CI 绿”；干净性只在 CI 断言。
4. **expected 文件无 schema 校验（P18）**：把 `schemaVersion` 改成 99 并给 `b2` 加未知字段 `bogusField` → `check:baseline` **exit 0**。`schemaVersion` 读了但从未比较，未知字段被忽略（`valueErrors` 只白名单比较）。
5. **`--accept` 是显式逃生门（P10/P11）**：`--accept` 会用**当前报告**（可能陈旧、也可能来自被改过的代码）重写 expected，只拒绝“空门/重复门/失败门”，并打印变更 diff。P10 实测：报告改成 `events: 669` 后 `--accept` exit 0、打印 `b2` 段 diff、expected 变 669、随后 `check` 变绿。这是设计上的“显式接受”，本身合规（R0 §5.1 允许），但它**不能**防止“先跑 accept 再宣称门绿”，只能靠 expected 是 tracked 文件、diff 可审。

### 4.2 门的内容敏感性（不只是计数）

P20 实测：把 `demos/world/src/rules/ambient.ts` 的 `severity: 0.4` 改成 `0.45`（只改事件 payload 里一个数值）→ 重新生成报告后 **12/12、13/13 门仍全 PASS**，事件数/来源不变，但 `check:baseline` **exit 1**，且只报 hash：
`b2.projectionHash 期望 fb6cb1e3 实际 12558484`、`b2.fullHash 期望 8b77f4ae 实际 24984e4d`、`b3.replayHash 期望 46c85469 实际 092c1b98`。
→ 说明 B2/B3 的哈希不是装饰：内容变化能在计数不变时被抓住。（上限：32 位哈希，见 §7。）

### 4.3 稳定性 / 环境无关性（实测）

### 10.6 新机制有效性：`report-stamp` 覆盖、盲区、伪造、忽略项

**覆盖是否正确（阅读 + 定向探针）**

| 检查 | 结果 |
|---|---|
| 指纹目录 | `src`(9) + `engine`(2) + `harness`(3) + `llm`(3) + `demos/world/src`(28) + `demos/world/fixtures`(20) = **65**，与印记 `sourceFiles=65` 一致 |
| canon 输入 | `loadCanon()` 的默认路径 `demos/world/fixtures/ferry-market.json`（`world/canon.ts:32`）→ **在覆盖范围内** |
| cassette 输入 | `demos/world/fixtures/llm-b3`、`fixtures/llm` → **覆盖**（也在报告 `cassettes` 计数内） |
| 跨 demo 依赖 | `demos/world/src` **不 import** `demos/embodied`（grep 无命中）→ 未覆盖 `demos/embodied` 不是盲区 |
| 报告文件 | 印记记录 `reports/world-validation.json`、`reports/world-b3-validation.json` 内容哈希 → 改写/替换即红（A1/F6） |

**盲区（实测/阅读）**

1. **stamp 可伪造（实测 G3）**：`writeStamp()` 是导出的普通函数、印记是本地 gitignored 文件、无签名/HMAC。改源码后不重生成、只调用 `writeStamp()` 刷新 sourceHash → `check:baseline` 从 **1 变 0**（陈旧报告通过）。即：**它能防“忘了重生成报告”，不能防“蓄意伪造”**。
2. **门槛文件本身不在指纹内**：`scripts/`（含 `report.mjs`、`baseline.mjs`、`report-stamp.mjs`）、`package.json`、`.github/` 不被指纹覆盖。若把 `report:world` 改成空操作，印记不会发现；但这些文件都是 tracked、CI/评审可见，属于“门自身被改”的威胁模型之外。
3. **Node/OS/环境变量不在指纹内**：跨平台报告差异（Windows vs Linux）不会被 stamp 发现，只能靠与 expected 的值/hash 比较（expected 是 Windows 生成的，Linux 若不同则 CI 会红——**未验证**，见 §10.9）。
4. **不需要的敏感**：覆盖目录内**纯注释变更**也会红（G1），这是“内容哈希”的必然；因为 `verify` 自带 `report:world`，对正常开发不构成误伤，只是单跑 `check:baseline` 时需要先重生成。
5. `readStamp` 取**最后一条可解析行**：多行印记时旧行被忽略（F9），行为确定；损坏行被跳过（F3 视为缺失）。
